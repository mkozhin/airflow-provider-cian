# airflow-provider-cian

Airflow-провайдер для сбора отчётов застройщиков (builder reports) через Cian API и выгрузки в BigQuery и S3-совместимые хранилища.

## Language

**Account (кабинет)**:
Один API-кабинет Cian с уникальным токеном доступа, принадлежащий одному застройщику.
_Avoid_: профиль, пользователь, клиент

**Account ID**:
Произвольная строковая метка кабинета, задаётся Airflow-администратором в поле `extra` коннектора (multi-account) или в `conn.login` (single-account). Не является числовым идентификатором из системы Cian. После санитизации (`[^\w-]` → `_`) используется **единообразно во всех употреблениях**: в filesystem-путях, S3/GCS-путях, Airflow TaskGroup ID, при поиске токена (`resolve_token`) и записывается полем `account_id` в **каждую запись выгрузки** (JSON и CSV, сразу после `id`) — не только в путь файла. Инвариант: оператор всюду работает с одной канонической (санитизированной) формой Account ID. В параметре оператора `account_id` хранится только `id` — токен никогда не сериализуется в метадата-БД Airflow.
_Avoid_: cabinet_id (в публичном API), user_id, cian_id

**Single-account mode**:
Режим работы оператора без параметра `account_id` — токен берётся из `conn.password`, Account ID берётся из `conn.login`. `conn.login` **обязателен**: без него таск падает с `AirflowException` до запроса к API. Путь файла всегда содержит сегмент кабинета.

**Multi-account mode**:
Режим работы DAG с несколькими кабинетами — список кабинетов читается из `extra.accounts` коннектора при парсинге DAG; на каждый кабинет создаётся отдельный `TaskGroup`.

**Builder Report (отчёт застройщика)**:
Запись о звонке или действии, привязанная к новостройке (`newbuilding`), которую возвращает Cian API за конкретную дату.

**Статус звонка (целевой / нецелевой)**:
В Cian нет отдельного поля статуса. Статус выводится из бюджета записи: если за звонком закреплён бюджет (`billing_price > 0`), звонок **целевой** (`is_targeted = true`), иначе — **нецелевой**. Бюджет может быть доначислен или изменён уже после первичной выгрузки, и тогда статус того же звонка меняется задним числом.
_Avoid_: status, status_id (это термины другого провайдера, в Cian такого поля нет)

**Пустой день (empty day)**:
Дата, за которую Cian вернул корректный ответ со `reports: []` — звонков и действий не было. За такой день оператор **не создаёт файл** и возвращает `None`; Airflow не пишет XCom, поэтому день выпадает из результата mapped-таска, а downstream mapped-таски за него не разворачиваются. Пустой день — это **штатное** состояние, не ошибка.
_Не путать с_ **сломанным ответом API**: ответ 200 без `result.reports` (или с не-списком, `null`, списком или строкой на верхнем уровне) — это дефект ответа, и он теперь **валит таск** с `AirflowException`, а не выдаётся за пустой день. Ровно этим пустой день отличается от битого ответа: `reports: []` — легитимно, отсутствие `reports` — нет.
_Avoid_: «нет данных» без уточнения (может значить и пустой день, и битый ответ)

**Snapshot (снапшот выгрузки)**:
Состояние данных Builder Report на момент конкретного запуска DAG. Поскольку бюджет (а значит, и статус звонка) меняется задним числом, одна и та же дата, выгруженная в разные запуски, даёт разные снапшоты. `snapshot_ts` помечает запись реальным временем старта прогона DAG (когда данные были фактически получены), позволяя в аналитическом слое отличать снапшоты и отслеживать историю изменения статуса.

**snapshot_ts vs datetime (две категории времени)**:
`datetime` — время *события*, полученное от Cian API (бизнес-данные о звонке): MSK с офсетом `+03:00`. `snapshot_ts` — метаданность *пайплайна*: когда данные были выгружены нами. Это разные категории, и формат их намеренно разделяет (`snapshot_ts` — naive-UTC без офсета). Оба поля имеют **секундную точность**: доли секунды из ответа API отбрасываются при парсинге `datetime` (см. `docs/adr/0005-datetime-drop-subsecond.md`), а `snapshot_ts` формируется без них изначально.

## Relationships

- Один **коннектор** (`cian_conn_id`) содержит один или несколько **Account**-ов
- В **single-account mode** коннектор содержит ровно один Account (токен в `conn.password`)
- В **multi-account mode** коннектор содержит список Account-ов в `extra.accounts`
- Каждый **Account** имеет ровно один токен и один **Account ID**
- Каждый **Account** пишет данные в отдельную BQ-таблицу (`{BQ_TABLE}_{account_id}`) и отдельный S3/GCS-префикс

## Flagged ambiguities

- `id` в `account["id"]` — это НЕ идентификатор из Cian API, а пользовательская метка для Airflow-пути и группировки задач.
- `login` в коннекторе — используется как Account ID для single-account mode; НЕ является логином для аутентификации в Cian API (аутентификация через `conn.password` — Bearer token).
- **Асимметрия `list_accounts` vs `resolve_token` при коллизии Account ID**: две записи `extra.accounts`, схлопывающиеся после санитизации в один Account ID (напр. `"a.b"` и `"a/b"` → `"a_b"`), обрабатываются по-разному. `list_accounts()` (построение списка кабинетов) **дедуплицирует** такую коллизию с WARNING и оставляет первую запись. `resolve_token()` (резолюция токена в момент выполнения) читает `extra.accounts` заново через `_parse_accounts` (без дедупликации) и на неоднозначной коллизии **падает** `AirflowException` — молчаливый выбор чужого токена опаснее явной ошибки на runtime. Дедуп в `list_accounts()` не влияет на то, что видит `resolve_token`: коллизирующий коннектор теперь громко падает в runtime для затронутого кабинета — это и есть задуманное поведение «fail-loud на неверной конфигурации».
