# Пустой день сигнализируется отсутствием XCom, а не `AirflowSkipException`

За дату, по которой Cian вернул `reports: []` (день без звонков), провайдер раньше всё равно создавал файл и DAG заливал его дальше: в S3 попадал объект на 0 байт (JSON) или с одним CSV-заголовком, а в BigQuery партиция за эту дату обнулялась `WRITE_TRUNCATE`-загрузкой пустого файла — тихая потеря данных при повторном прогоне бэкфила. «Пустой день не должен порождать файл» — понятно; неочевиден **механизм**, которым оператор сообщает downstream-таскам «за эту дату заливать нечего». Этот ADR фиксирует выбор механизма, потому что альтернатива, которая кажется естественной (`AirflowSkipException`), на проде пользователя (Airflow 2.9.1) ломает выгрузку целиком.

## Решение

Оператор `CianBuilderReportsOperator.execute()` за пустой день **возвращает `None`** (файл не создаётся). За день с данными он возвращает самоописывающий словарь `{"date": ..., "path": ...}`.

- Airflow **не пишет XCom для `None`** (`models/taskinstance.py`), инстанс остаётся `success`, а пустой день **выпадает из списка** результатов mapped-таска `collect`. Downstream mapped-таски (`upload_gcs` / `upload_s3` / `load_bq`) разворачиваются только по дням с данными — инстансов за пустые дни не появляется вовсе.
- `AirflowSkipException` за пустой день **сознательно не бросается.**

## Контекст и обоснование

Рассматривались два варианта сигнализации пустого дня.

**Вариант A — `raise AirflowSkipException` за пустой день (отклонён).** Интуитивно «пропустить день» — это и есть skip. Но в текущей форме `bq_and_s3_dag.py` / `bq_and_s3_multi_account_dag.py` между `collect` и заливкой стоит агрегатор `make_*_params` с дефолтным trigger rule `all_success`. **Проверено экспериментально прогоном `dag.test()` на Airflow 2.9.1** (не выведено из чтения кода): один пропущенный map-инстанс `collect` делает `skipped` весь downstream-таск `make_*_params`, потому что `all_success` считает состояния по **всем** map-индексам разом (`ti_deps/deps/trigger_rule_dep.py`, счётчик `_UpstreamTIStates.calculate`). В результате за прогон не выгружается **ни одна** дата, включая даты с данными. Один день без звонков глушит весь бэкфил — регрессия хуже исходного бага.

**Вариант B — вернуть `None` (выбран).** Опирается на штатную семантику Airflow «нет XCom — нет элемента в списке». **Тем же прогоном подтверждено:** `None` из mapped-таска не пишется в XCom, инстанс остаётся `success`, downstream получает `LazyXComAccess` только с непустыми днями (упорядоченный по map-индексу), trigger-правила downstream при этом не нарушаются. Смешанный период (часть дней пустая, часть с данными) выгружается корректно — заливаются ровно дни с данными.

Ключевое отличие: вариант A завязан на межиндексную семантику trigger rule и потому «заражает» skip-ом весь таск; вариант B работает на уровне отдельного элемента списка и потому изолирует пустой день, не трогая соседей.

Возврат **самоописывающего словаря** (а не голого пути-строки) за день с данными — вторая половина решения. Раньше downstream собирал kwargs через `zip(paths, dates)`, что при выпадении любого дня из `paths` молча смещало все последующие даты. Когда каждый элемент несёт свою дату внутри себя, это смещение становится **невозможным по конструкции**: агрегатору больше нечего zip-ать, он читает `item["date"]` и `item["path"]` из одного объекта.

## Последствия

- **Агрегаторы обязаны писать `items = list(items or [])` первой строкой.** Когда пуст **весь** период, ни один инстанс не записал XCom, и Airflow отдаёт агрегатору `None`, а не `[]` (проверено прогоном; наивный `len(items)` падает с `TypeError: object of type 'NoneType' has no len()`). Это зафиксировано в README обоих языков и покрыто прямыми юнит-ассертами `make_*_params(None) == []` — самой тонкой точкой всей правки.
- **Класс ошибок «смещение дат» устранён по построению.** `grep -rn "zip(paths" examples/` пуст; каждый элемент списка знает свою дату.
- **Полностью пустой период в v1/multi-account даёт `skipped`, но безопасный.** Агрегатор возвращает `[]`, mapped-таск заливки разворачивается в ноль инстансов, Airflow помечает его `skipped`, `dag_run` остаётся `success`. Это ноль-expand, а не заражение skip-ом из варианта A, — соседние даты (если бы они были) не пострадали бы.
- **v2 ведёт себя иначе — `skipped` там не бывает.** В `bq_and_s3_dag_v2.py` отдельных mapped upload-тасков нет: GCS, BQ и S3 вызываются внутри одного `process_date`. Пустой день — это `process_date`, вернувший `None` в состоянии `success`; пропускаются только побочные эффекты заливки. `skipped` не возникает даже когда пуст весь период. Не путать две формы DAG.
- **Связь с ADR-0002.** Возврат оператора сериализуется в XCom, поэтому его форму провайдер контролирует на уровне архитектуры. ADR-0002 фиксирует, что в XCom **не** попадает (токен); этот ADR — что именно туда попадает за день с данными (`{"date", "path"}`) и что за пустой день не попадает ничего.
