# `account_id` пишется в каждую запись выгрузки; `login` обязателен; санитизация единообразна

При загрузке файлов от нескольких кабинетов в одно хранилище (BigQuery/S3) принадлежность записи кабинету раньше была видна **только из пути файла**. После загрузки в общую таблицу это знание терялось: строки разных кабинетов становились неразличимы в самих данных. Этот ADR фиксирует решение писать Account ID полем `account_id` в каждую запись выгрузки, сопутствующее ужесточение (`login` обязателен) и инвариант единообразной санитизации — потому что все три решения дорого обратить: поле уходит в downstream-данные, как `snapshot_ts` в ADR-0001.

## Решение

1. **`CianBuilderReportsOperator` пишет `account_id` в каждую строку выгрузки** (JSON и CSV), вторым полем сразу после `id`. Значение — санитизированный Account ID кабинета, ровно то же, что попадает в сегмент пути файла (в `execute()` в данные передаётся локальный `cabinet_id`, а не `self.account_id`). Базовая схема растёт с 18 до 19 полей; `snapshot_ts` при `add_snapshot_ts=True` становится 20-м полем JSON.
2. **`login` в коннекторе обязателен для single-account режима.** Валидация делается один раз в `execute()` сразу после `resolve_cabinet_id()` — до создания hook и запроса к API: `if not cabinet_id` → `AirflowException`. Условие `not cabinet_id` (а не `is None`) отсекает и `None` (single-account без `login`), и пустую строку `account_id=""`.
3. **Санитизация Account ID единообразна во всех употреблениях.** `resolve_cabinet_id()` в multi-account ветке прогоняет значение через `Account(id=account_id).id`, `resolve_token()` санитизирует ключ поиска. Инвариант: оператор всюду (путь, данные, поиск токена) работает с одной канонической (санитизированной) формой.

## Контекст и обоснование

**Почему поле, а не только путь.** Путь файла — метаданность транспорта: после загрузки в BigQuery он не сохраняется в строках. Чтобы принадлежность кабинету пережила загрузку, она должна быть **в данных**. Это то же соображение, что и в ADR-0001 для `snapshot_ts`: значение, попадающее в аналитический слой, должно быть в записи, а не выводиться из имени файла.

**Почему `account_id` без opt-in флага (в отличие от `snapshot_ts`).** `snapshot_ts` опционален, потому что он меняет семантику дедупликации и нужен не всем. `account_id` — базовый идентификатор строки: в multi-account сценарии без него данные некорректны (строки неразличимы), а в single-account он безвреден. Опциональность порождала бы схемы двух видов и была бы источником ошибок. Цена — ломающее изменение схемы, оправданное релизом 0.5.0.

**Почему `login` обязателен.** Раньше single-account без `login` писал путь без сегмента кабинета и (после этой правки) писал бы пустой `account_id`. Пустая строка в `os.path.join(base_dir, "", ...)` молча съедает сегмент — это тихий дефект. Fail-fast с понятной ошибкой до запроса к API дешевле, чем молчаливо испорченные путь и данные.

**Почему имя `account_id`, а не `cabinet_id`.** Совпадает с термином глоссария **Account ID** (CONTEXT.md), с кодом (`accounts.py`, параметр оператора `account_id`) и с именованием BQ-таблиц `{BQ_TABLE}_{account_id}`. Вариант `cabinet_id` отвергнут — он в списке _Avoid_ глоссария (гриль-сессия 2026-07-21).

**Почему единообразная санитизация.** До правки `resolve_cabinet_id()` в multi-account ветке возвращал сырой `account_id`, а путь строился из санитизированного — рассинхрон был возможен при сыром вводе. Единый инвариант «одна каноническая форма всюду» делает сырой ввод (`"a.b"`) работающим end-to-end: и путь, и поле, и поиск токена дают `"a_b"`. Для штатного пути через `list_accounts()` поведение не меняется (санитизация идемпотентна). Побочный эффект: сырые метки типа `" "` превращаются в `"_"` — garbage in, garbage out, дополнительной валидации не делаем.

**Cian API не даёт реального id кабинета.** По swagger (`https://public-api.cian.ru/builders/swagger/latest`, проверено 2026-07-21) нет эндпоинта «кто я» и нет полей `builderId`/`accountId` в ответах. Поэтому `account_id` — **пользовательская метка** из коннектора, а не значение из Cian. В README рекомендуется брать ИНН или название юрлица из договора.

## Последствия

- **Схема downstream-таблиц BigQuery должна получить колонку `account_id STRING` до деплоя 0.5.0.** У `GCSToBigQueryOperator` и load job BigQuery `ignore_unknown_values=False` по умолчанию — новое поле, отсутствующее в схеме, сломает загрузку. `BQ_SCHEMA` во всех трёх примерах обновлены (v1/v2: 19 полей; multi-account: 20); regression-тесты сверяют состав `BQ_SCHEMA` с `_CSV_FIELDS`.
- **Исторические данные провайдер НЕ мигрирует.** Это ломающее изменение; потребитель сам решает, что делать со старыми строками (миграция, пересборка, NULL). Решение гриль-сессии 2026-07-21.
- **Single-account инсталляции должны заполнить `login`** в коннекторе `cian_default` до обновления, иначе таски начнут падать (это и есть цель fail-fast).
- **Значение `account_id` уходит в выгрузки** — менять формат/санитизацию задним числом дорого (ломает консистентность исторических данных). Отсюда и этот ADR.
- **Связь с ADR-0002/0003.** ADR-0002 фиксирует, что в XCom **не** попадает (токен); ADR-0003 — что попадает за день с данными (`{"date", "path"}`). Этот ADR — про содержимое **самой записи** выгрузки: `account_id` теперь её часть. XCom-контракт `{"date", "path"}` не меняется.
