# `accounts.py`: сегрегированный интерфейс `resolve_cabinet_id` / `resolve_token`

Модуль `airflow_provider_cian.accounts` предоставляет **две раздельные функции** для резолюции account:

- `resolve_cabinet_id(conn_id, account_id) -> str | None` — возвращает идентичность кабинета (cabinet ID), токена не касается.
- `resolve_token(conn, account_id) -> str` — возвращает токен аутентификации, cabinet ID не возвращает.

Функция вида `resolve() -> (cabinet_id, token)`, возвращающая оба значения разом, сознательно **не создаётся**.

## Решение

Интерфейс резолюции сегрегирован по принципу «один потребитель — один метод»:

- **Оператор** (`CianBuilderReportsOperator`) вызывает только `resolve_cabinet_id` и записывает результат в XCom.
- **Хук** (`CianHook._make_request`) вызывает только `resolve_token` для формирования заголовка `Authorization`.

Оператор физически не имеет доступа к токену — он вызывает функцию, которая токен не возвращает.

## Контекст и обоснование

**Инвариант безопасности: токен не попадает в метадату Airflow.**
Airflow сериализует возвращаемое значение `execute()` в таблицу XCom метадата-БД. Если токен попал бы в возвращаемое значение оператора — прямо или косвенно через кортеж `(cabinet_id, token)` — он оказался бы в открытом виде в БД Airflow, логах шедулера и XCom UI. Это нарушение изоляции секретов независимо от того, используется ли значение `xcom_push` явно.

**Почему объединённый `resolve() -> (cabinet_id, token)` опасен.**
Такая функция возвращала бы токен в точку вызова оператора. Даже если разработчик не планирует использовать токен в операторе, он оказался бы доступен локальной переменной в `execute()` — риск случайной утечки (в лог, в XCom, в исключение с полным traceback) возрастает. Сегрегация устраняет саму возможность, а не полагается на дисциплину вызывающего.

**Разделение зон ответственности.**
Оператор отвечает за координацию: какой кабинет, какой период, куда писать результат. Хук отвечает за HTTP-транспорт и аутентификацию. Инвариант «хук знает токен, оператор — нет» закреплён на уровне публичного API модуля, а не только соглашения в коде.

**Связь с ADR-0001.** Оба ADR касаются границ провайдера: ADR-0001 фиксирует, что именно попадает в *данные* (формат `snapshot_ts`), ADR-0002 — что именно попадает в *метадату Airflow* из оператора. Общий принцип: провайдер контролирует, что сериализуется Airflow, на уровне архитектуры, а не только кода.

## Последствия

- Оператор никогда не импортирует и не получает токен. Это статически проверяемо: `grep resolve_token airflow_provider_cian/operators/` должен возвращать пустой результат.
- **Не сливать функции обратно.** Если появится желание создать `resolve() -> (cabinet_id, token)` ради «удобства» или «DRY» — это нарушает инвариант безопасности. Объединённая функция обязательно потребует вызова из оператора или возврата через него, что неприемлемо.
- Асимметрия сигнатур (`conn_id` vs `conn`) намеренна: `resolve_cabinet_id` принимает `conn_id` и читает коннектор лениво (в multi-режиме не читает вовсе), `resolve_token` принимает уже полученный `conn` — хук всё равно читает коннектор для `base_url`, лишний `get_connection` не нужен.
