# Отбрасывание долей секунды в поле `datetime`

## Overview

**Что делаем.** В `CianBuilderReportsOperator._enrich` перед парсингом времени из ответа Cian API отбрасываем дробную часть секунды. Поле `datetime` в выходных записях всегда имеет формат `YYYY-MM-DDTHH:MM:SS+03:00` — ровно тот, что уже задокументирован в README.

**Какую проблему решает.** Прод-таск падает с `ValueError` на записях, где Cian вернул время с 5-значной дробной частью. Правка убирает целый класс отказов (любая нестандартная разрядность долей секунды) вместо того, чтобы поддерживать каждый вариант по отдельности.

**Как встраивается в систему.** Изменение локальное — одна точка парсинга в `_enrich`. Формат выхода приводится к уже заявленному контракту; downstream (JSON → GCS → BigQuery, JSON → S3) доли секунды не использует.

---

## Проблема: что именно сломалось

### Симптом

Прод-инцидент, DAG `osnova_cian`, run `scheduled__2026-07-23T02:20:00+00:00`, таск `cabinet_100986436.collect` (map_index=0), 3 попытки — все упали:

```
File ".../airflow_provider_cian/operators/builder_reports.py", line 157, in _enrich
    dt = _datetime.fromisoformat(raw_dt.replace("Z", "+00:00"))
ValueError: Invalid isoformat string: '2026-07-23T18:14:20.86363+03:00'
```

### Причина

Cian API отдаёт время с **нестабильной разрядностью долей секунды**. В историческом трафике встречались значения без дробной части (все существующие тесты построены на них), теперь пришло значение с **5 знаками**: `.86363`.

`datetime.fromisoformat()` в CPython **до 3.11** — не полноценный ISO-8601-парсер, а обратная операция к `datetime.isoformat()`. Он принимает дробную часть **только длиной 3 или 6 знаков** (миллисекунды или микросекунды). Любая другая разрядность (1, 2, 4, 5, 7+) — `ValueError`.

Airflow-воркер работает на **Python 3.10**, провайдер объявляет `requires-python = ">=3.10"` (`pyproject.toml:10`). В Python 3.11+ парсер переписан и такую строку принял бы — но воркер обновить мы не можем и минимальную версию провайдера поднимать не собираемся, поэтому опираться на 3.11 нельзя.

### Почему это не единичный случай

Разрядность долей определяется сериализатором на стороне Cian и от нас не зависит. Сегодня пришло 5 знаков, завтра может прийти 1, 2, 4 или 7. Точечная поддержка «ещё одного варианта» не закрывает проблему — закрывает её только отказ от долей секунды как таковых.

## Решение и обоснование

### Решение

Перед `fromisoformat()` удалять дробную часть секунды регулярным выражением. Результат — секундная точность на входе и, как следствие, на выходе.

### Почему отбрасывание, а не поддержка

1. **Доли секунды не нужны на всём пути данных.** В JSON-выгрузке их никто не читает; в BigQuery поле `datetime` грузится как `STRING` (см. `BQ_SCHEMA` в примерах DAG), то есть даже типизированного парсинга времени там нет; в S3 лежит тот же JSON. Ни одна витрина субсекундную точность не использует. Это подтверждено владельцем данных.
2. **Формат уже задокументирован без долей.** `README.md:118` и `README_ru.md:117` описывают `datetime` как `YYYY-MM-DDTHH:MM:SS+03:00`. Текущий код этот контракт нарушает: при 6-значных долях `dt.isoformat()` вернул бы `2026-07-23T18:14:20.863630+03:00`. Правка **приводит код к доке**, а не меняет контракт.
3. **Согласуется с соседним полем.** `snapshot_ts` уже формируется как `strftime("%Y-%m-%dT%H:%M:%S")` — без долей. После правки оба временных поля записи имеют секундную точность.
4. **Минимум кода.** Одна константа + одна строка вместо ветвления по разрядности, нормализации padding-ом или зависимости от внешнего парсера.

### Про «менять форматы дорого» (ADR-0001)

ADR-0001 фиксирует: формат `snapshot_ts` менять задним числом дорого, потому что ломает консистентность исторических снапшотов в BigQuery. Здесь этот аргумент **не срабатывает**, и важно объяснить почему:

- Меняется не `snapshot_ts`, а `datetime`, и не смысл поля, а только разрядность. **Точный аудит исторических данных не проводился**, и утверждать «долей в истории не было» нельзя: 3- и 6-значные доли парсились бы успешно и попадали бы в выход незамеченными (падение вызывают только «неправильные» разрядности). Честная формулировка: такие значения в истории возможны, их усечение — сознательное решение владельца данных, известных потребителей субсекундной точности нет.
- Тип в BigQuery — `STRING` (см. `BQ_SCHEMA` в `examples/bq_and_s3_dag.py`), схема не меняется, перезагрузка исторических партиций не требуется.
- Downstream-потребителей субсекундной точности нет.

То есть исторические данные остаются валидными, а новые становятся строго соответствующими доке. Дорогой миграции, о которой предупреждает ADR-0001, здесь не возникает.

**Прецедент в самом проекте.** Версия 0.1.3 (CHANGELOG) изменила значение выходного поля `date` — «always equals the operator's `date` parameter instead of the Moscow calendar date» — и была выпущена **патч-версией**. Это прямо отвечает на вопрос «почему 0.5.1, а не 0.6.0»: изменение значения поля без изменения схемы в этом проекте уже трактовалось как fix.

### Отклонённые альтернативы

| Вариант | Почему отклонён |
|---|---|
| Нормализовать доли до 6 знаков (padding `.86363` → `.863630`) и парсить | Сохраняет данные, которые нам не нужны, и добавляет код ради них; в выходе появляются `.863630`, что расходится с доком |
| `try/except` с фолбэком на второй парсер (`dateutil`, `strptime` по нескольким маскам) | Новая зависимость либо перебор форматов; тот же результат, больше кода и веток |
| Поднять минимальную версию до Python 3.11 | Не в нашей власти: воркер Airflow на 3.10; это ломает совместимость провайдера ради несущественной точности |
| Обернуть `ValueError` в `AirflowException` с понятным текстом | Полезно для диагностики, но это отдельная задача про качество ошибок, а не про этот баг; сознательно вне scope, чтобы правка осталась минимальной |

### Последствия, которые нужно принять

- **Усечение, а не округление.** `18:14:20.86363` → `18:14:20`, не `18:14:21`. Для звонков это несущественно, идентичность записи определяется полем `id`.
- **Формальное изменение выхода.** Если бы Cian прислал 3- или 6-значные доли (сейчас парсится успешно), до правки они попали бы в `datetime`, после — будут отброшены. Фиксируем это в CHANGELOG явно.
- **Регекс анкерится к позиции секунд времени.** Наивный `\.[0-9]+` резал бы точку в любой позиции строки: на битом входе (например `23.07.2026`) он мутировал бы строку до парсинга, и `ValueError` показал бы изменённое значение вместо того, что реально прислал Cian. Вариант `(?<=:[0-9]{2})\.[0-9]+` тоже небезопасен: он привязан к любому `:NN`, поэтому битую строку `2026-07-23T18:14:20+03:00.5` (сейчас — честный `ValueError`) он **молча превратил бы в валидную** `2026-07-23T18:14:20+03:00`, то есть тихо исказил бы данные. Итоговый вариант — lookbehind фиксированной длины по `HH:MM:SS`: `(?<=[0-9]{2}:[0-9]{2}:[0-9]{2})\.[0-9]+`. Проверено на Python 3.10: прод-строка усекается, пробельный разделитель тоже покрыт, а `2026-07-23T18:14:20+03:00.5` и `23.07.2026` остаются нетронутыми и честно падают/парсятся как раньше.

## Solution Overview

Единственная точка изменения — `_enrich`. Добавляется модульная константа с регексом и одна строка нормализации перед парсингом:

```python
# Cian sends sub-second digits at an unstable precision, and fromisoformat() below
# Python 3.11 accepts only 3 or 6 of them — 5 digits killed a prod task. Sub-second
# precision is not used anywhere downstream, so it is dropped (see ADR-0005).
# Anchored to HH:MM:SS so a malformed value reaches fromisoformat() unmodified;
# [0-9] rather than \d, which is Unicode-aware (same convention as the `date` check).
_FRACTIONAL_SECONDS_RE = re.compile(r"(?<=[0-9]{2}:[0-9]{2}:[0-9]{2})\.[0-9]+")
```

```python
raw = _FRACTIONAL_SECONDS_RE.sub("", raw_dt.replace("Z", "+00:00"))
dt = _datetime.fromisoformat(raw)
```

Дальнейшая логика (`tzinfo is None → MSK`, иначе `astimezone(_MSK)`, `dt.isoformat()`) не меняется: у `dt` теперь `microsecond == 0`, поэтому `isoformat()` возвращает `...HH:MM:SS+03:00`.

Анкер по `HH:MM:SS` (а не по `THH:MM:SS`) выбран сознательно: `fromisoformat` допускает **любой** одиночный разделитель даты и времени, поэтому вход вида `2026-07-23 18:14:20.5+03:00` (с пробелом) при анкере по `T` остался бы с долями. Cian такой формат не отдавал, но инвариант «точки в выходе нет» должен быть честным. Проверено на 3.10, что ослабление анкера **не** ломает защиту от тихого искажения: `2026-07-23T18:14:20+03:00.5` по-прежнему не «чинится» (перед точкой стоит `20+03:00`, что под `[0-9]{2}:[0-9]{2}:[0-9]{2}` не подпадает) и `23.07.2026` не трогается.

## Technical Details

- **Вход:** `record["date"]` — строка ISO-8601 от Cian API, с офсетом или без, с долями секунды или без, возможно с `Z` вместо `+00:00`.
- **Нормализация:** `Z` → `+00:00` (как было), затем удаление дробной части, идущей сразу за секундами (`(?<=[0-9]{2}:[0-9]{2}:[0-9]{2})\.[0-9]+`).
- **Порядок операций:** сначала `replace("Z", ...)`, затем `sub` — порядок не критичен (`Z` стоит в конце строки, точка — перед офсетом), но фиксируется для читаемости.
- **Выход:** `row["datetime"]` — строка `YYYY-MM-DDTHH:MM:SS+03:00`.
- **Незатронутое:** `row["date"]` (всегда параметр оператора), `snapshot_ts` (уже без долей), состав и порядок полей, CSV-схема.
